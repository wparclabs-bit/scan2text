- **2026-08-23 (S23-DIAG-ZOMBIE-BACKEND-KILL-TREE):** DIAG — **ROOT CAUSE: KILL_SILENT_FAILURE via backend daemonization + PID-targeted kill.** Closing the Tauri shell leaves `scan2text-backend.exe` alive (~65MB, holding port 47351), violating NFR-05 / FIX77. Forensics: spawn wiring correct (`BackendManager.start()` → `start_backend()`, `self.child = Some(child)` at backend_process.rs:66); kill wiring correct and present in the deployed binary — `RunEvent::WindowEvent::CloseRequested` (lib.rs:398) → `guard.stop()` (lib.rs:402) → `stop_backend()` (backend_process.rs:285) → `taskkill /F /T /PID <pid>`. Deployed shell hash MATCHES release target (`8CDF8DD6…`), so NOT a stale deploy. Live probe (WM_CLOSE) reproduced the zombie: shell dies, inner daemon survives, port held. **New mechanism found:** the Python backend *daemonizes* — the process Rust spawns (outer) spawns a second `scan2text-backend.exe` (inner Uvicorn daemon that holds 47351) and exits within ~2s. Rust tracks the outer PID as `self.child`; on close `taskkill /F /T /PID <outer_pid>` reports "process not found" (outer already gone), the `log::warn!` is invisible in release (no logger installed — plugin only added under `cfg(debug_assertions)`, lib.rs:367), and the native `child.kill()` fallback no-ops on the dead child → inner daemon survives silently. Kill command uses `/PID` not the CEO-locked `/IM scan2text-backend.exe`, so it cannot catch the daemonized inner. Recommended remediation (NOT implemented): kill by image name per locked intent (`taskkill /F /IM scan2text-backend.exe /T`) or track the inner daemon's PID from its PID file; add a release logger so kill-path failures surface. Full report: `second-brain/01-Agent-Memory/Phase-11/diag-S23-ZOMBIE-BACKEND-KILL-TREE.md`.
